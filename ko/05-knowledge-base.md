# Spec와 지식 베이스: 에이전트가 정말 읽었는지, 정말 따르는지 확인하기

프로젝트에 CLAUDE.md를 쓰고, 규칙 몇 개를 떼어내고, skill을 몇 개 만들고, MCP 서버를 두 개 연결했다. 그런데도 에이전트는 늘 하던 실수를 그대로 하고, 정해 둔 규칙을 못 본 척한다.

이쯤 되면 한 가지가 의심스러워진다. 도대체 읽기는 한 걸까?

이 질문은 보기보다 값지다. "파일을 하나 설정했다"와 "그 파일의 내용이 이번 단계에서 모델의 판단에 실제로 영향을 줬다" 사이에는 여러 관문이 있고, 어느 관문에서든 조용히 흘릴 수 있다. 나는 이를 흔히 하나로 뭉뚱그려지는 네 가지로 나눈다.

> **연결 ≠ 로드 ≠ 읽힘 ≠ 준수.**

`.claude/`에 파일을 두는 것은 "연결". 그것이 이번 세션에서 컨텍스트 윈도에 끼워지는 것은 "로드". 모델이 현재 단계에서 그것을 실제로 판단에 반영하는 것은 "읽힘". 그대로 행동해야 비로소 "준수". 네 가지 중 어느 하나라도 끊기면 결과는 똑같이 "규칙이 안 먹혔다"지만, 어디서 끊겼는지에 따라 디버깅 방식은 완전히 달라진다.

이 장에서는 먼저 지식 베이스를 연결하는 몇 가지 방식을 훑고, 다음으로 각 방식이 "언제·어떤 형태로" 컨텍스트에 들어가는지 설명하며, 마지막으로 그것이 정말 들어갔는지·정말 제약했는지 확인하는 법을 다룬다. 늘 그렇듯 Claude Code(이하 CC)와 Codex를 나란히 본다. CC 쪽은 공식 문서에 근거해 보수적으로 표현하고, Codex 쪽은 소스 줄 번호까지 짚을 수 있는 것은 출처를 달았다.

## 1. 지식 베이스가 에이전트에 닿는 경로

먼저 "지식 베이스"를 분명히 하자. 여기서는 에이전트가 계속 지켜 주길 바라는 것들——프로젝트 관례, 코딩 규약, 워크플로, 도메인 지식, 호출 가능한 능력, 외부 데이터를 가리킨다. 이것들을 에이전트에 연결하는 메커니즘은 CC와 Codex에서 대체로 일대일로 대응한다.

| 메커니즘 | Claude Code | Codex |
|---|---|---|
| 주 지시 파일 | CLAUDE.md: 프로젝트 / 사용자 / 조직 스코프, 더해 하위 디렉터리의 CLAUDE.md | AGENTS.md: 전역 / 프로젝트 / 하위 디렉터리 다단계 |
| 분할 규칙 | `.claude/rules/`: 여러 파일로 분할, 파일 경로로 스코프 지정 가능 | config 내 instructions: 설정을 따라다니는 지시 |
| 자동 메모리 | Auto memory: 모델이 스스로 모으는 메모, 입구는 `MEMORY.md` | —— |
| 스킬 | Skill: 트리거 조건이 있는 로드 가능한 행동 단위 | skill: 같은 개념, 호칭이 약간 다름 |
| 외부 도구 / 데이터 | MCP | MCP |
| 특수 주입구 | `@import`, `--append-system-prompt` | —— |

이 경로들은 비슷해 보이지만, 결정적인 차이는 모두 다음 절에 있다. 컨텍스트에 들어가는 "타이밍"과 "형태"가 다르다는 것, 그것이 "설정했는데 안 먹힌다"의 근원이다.

## 2. 각 경로는 어떻게 컨텍스트에 들어가나

차이는 세 가지에 숨어 있다. 언제 컨텍스트에 들어가는가, 어떤 신분으로 들어가는가, 어디서 조용히 새는가. 먼저 골격을 표 하나로 보이고, 소스 출처는 표 아래에 둔다.

| 경로 | 언제 컨텍스트에 들어가나 | 어떤 신분 / 형태로 | 가장 걸려 넘어지는 지점 |
|---|---|---|---|
| CLAUDE.md / AGENTS.md | 시작 시 "시작 디렉터리에서 위로" 가는 사슬이 로드됨. 하위 디렉터리의 것은 에이전트가 실제로 그 디렉터리의 파일을 읽으러 가야 들어옴 | user 메시지로 주입되며 system prompt가 아님——context이지 강제 설정이 아님 | 이번에 건드리지 않은 하위 디렉터리 규칙은 계속 부재. AGENTS.md는 기본 32 KiB 상한, 넘으면 잘림(무시가 아니라, 안 들어간 것) |
| `.claude/rules/` | `paths:` 있는 것은 glob 경로로 트리거. `paths` 없는 것만 시작 시 전량 로드 | CLAUDE.md와 같이 user 쪽에 실림 | `paths`를 적었는데 해당 디렉터리를 안 건드림 → 규칙이 발화 안 함. 버그가 아니라 설계 |
| skill | 시작 시에는 메타데이터(이름 + `description`)만 들어옴. 본문은 트리거돼야 로드 | progressive disclosure: 안 쓰면 토큰을 거의 안 먹지만, 한 번 로드되면 이후 매 턴 상주 | `description`이 매치 안 됨 → 본문은 한 글자도 안 들어옴. "발견 / 로드 / 트리거"는 별개의 셋 |
| MCP | 도구 정의(schema)가 시작 시 컨텍스트에 들어옴 | 토큰을 먹는 도구 목록 | 많이 마운트하고 각 도구도 많음 → 먼저 큰 컨텍스트 "임대료"를 냄 |
| 권한 / hook | 도구가 실제로 실행되기 직전에 가로챔, **모델의 의지를 거치지 않음** | 클라이언트 측 하드 제약, 위 "컨텍스트에 들어가는" 사슬 밖 | "모델이 어떻게 생각하든 막고 싶다"면 CLAUDE.md에 쓰지 말고 deny 규칙이나 PreToolUse hook을 쓸 것 |

기억할 만한 세부와 출처 몇 가지:

- **CLAUDE.md**: 공식 규정은 context이지 enforced configuration이 아니다. 거기 쓰는 "반드시 / 절대"는 본질적으로 스위치가 아니라 요청이다. `@import`는 시작 시 전개, 최대 4홉. 블록 레벨 HTML 주석은 주입 전에 벗겨지므로, 토큰을 안 먹고 사람에게 메모를 남기는 데 쓸 수 있다.
- **AGENTS.md**: 다단계 발견은 `core/src/agents_md.rs`, 32 KiB 상한은 `AGENTS_MD_MAX_BYTES`(`core/src/config/mod.rs:186`). `# AGENTS.md instructions ...` / `</INSTRUCTIONS>` 태그로 감싼 user 지시(`core/src/context/user_instructions.rs`)로, config instructions와 병합된다.
- **skill**: 목록 내 메타데이터에는 상한이 있어, `description` + `when_to_use` 합산 1536자를 넘으면 잘림. Codex 쪽은 메타데이터를 예산에 맞춰 렌더링해 developer 메시지에 끼워 넣는다(`core/src/session/mod.rs`의 `build_available_skills`).
- **MCP**: 도구는 연결 매니저에서 열거하고, 접근 가능하며 활성화된 것만 걸러 지시에 끼운다(`core/src/connectors.rs`).
- **권한**: CC는 `allow` / `ask` / `deny` 세 배열로, 판정은 deny > ask > allow, 거기에 permission mode(default / acceptEdits / plan / bypassPermissions)를 겹친다. Codex는 타입 시스템에 녹인다——`SandboxPolicy` 네 값(`protocol/src/protocol.rs:878`), `AskForApproval` 다섯 값(`:784`), 세분화된 `GranularApprovalConfig`(`:817-854`)가 skill / rules / MCP 각각에 매번 확인 여부를 따로 관리할 수 있다.

이 절을 한마디로 맺으면: **CLAUDE.md / 규칙 / skill 안의 말은 모델에게 보여 주는 제안이고, 권한과 hook은 당신을 대신해 동작을 막는 게이트다. "반드시"가 필요하면 후자를 쓴다.**

## 3. 에이전트가 정말 읽었고 정말 제약됐는지 어떻게 확인하나

이것이 이 장이 가장 풀어야 할 질문이다. 앞의 "연결 ≠ 로드 ≠ 읽힘 ≠ 준수" 사슬을 분해하면, 검증 수단도 두 층으로 나뉜다. 하나는 무언가가 컨텍스트 윈도에 들어갔는지(정적), 다른 하나는 에이전트가 실제로 무엇을 했는지(행동).

### 먼저: 그것이 정말 컨텍스트에 들어갔나

CC에는 기성 창구가 몇 개 있다.

- **`/context`**: 현재 컨텍스트 윈도의 토큰 분포를 본다——system prompt, 도구, MCP, 메모리 파일, 메시지가 각각 얼마를 차지하는지. 가장 직접적인 판단은, 로드됐다고 여긴 것이 여기서 몫이 없으면 안 들어간 것이다.
- **`/memory`**: 이번 세션에서 실제로 로드된 CLAUDE.md, CLAUDE.local.md, rules 파일을 열거한다. 이 목록에 없는 파일은 모델이 볼 수 없다. "CLAUDE.md가 안 먹힌다"의 디버깅은, 먼저 이걸 돌려 파일이 목록에 있는지 확인하는 데서 시작한다.
- **`InstructionsLoaded` hook**: 정확한 로그가 필요하면, 이 hook으로 어떤 지시 파일이·언제·왜 로드됐는지 기록할 수 있다. path-scoped 규칙과 하위 디렉터리의 지연 로드 파일을 디버깅하는 데 특히 좋다.

앞의 메커니즘에서 직접 도출되는 확인 동작도 몇 가지: 하위 디렉터리의 CLAUDE.md, `MEMORY.md`의 200줄 너머 내용, topic 파일은 시작 시 컨텍스트에 들어오지 않는다. 먹히는지 확인하려면, 모델이 실제로 해당 디렉터리의 파일을 read하러 갔는지 본다. `/compact` 후, 프로젝트 루트의 CLAUDE.md는 디스크에서 다시 읽혀 재주입되지만 하위 디렉터리의 것은 안 된다. 압축 후 규칙이 "느슨해지는" 것은 대개 이 때문이다.

### 다음: 에이전트가 실제로 무엇을 했나

정적 점검은 "그것이 윈도에 있는가"는 알려주지만, "그 skill이 이번에 정말 트리거됐는가" "파견한 서브에이전트가 당신의 규칙을 상속했는가"에는 답하지 못한다. 이것들은 행동 층의 문제로, 실제 한 번의 실행 트레이스를 봐야 한다.

이 층에는 오픈소스 프로파일러, 예컨대 [cctrace](https://github.com/androidZzT/cctrace)(Go 작성, MIT, 로컬 실행, 비통신)를 쓸 수 있다. 당신의 에이전트를 한 겹 감싸(`cctrace claude -- claude` 또는 `cctrace codex -- codex`), 그 실행의 이벤트를 로컬 워터폴 타임라인으로 펼친다. 이 장의 질문에 딱 맞물리는 기능이 몇 가지 있다.

- 세션 시작 시 "이 머신에서 어떤 skill이 발견됐는지, 그리고 그 description"을 모으고, 타임라인에 "이번에 어떤 skill이 실제로 트리거됐는지"를 표시한다. 둘을 대조하면 판단할 수 있다. 어떤 skill이 목록에 있는데 내내 한 번도 fire하지 않았다면, 그 `description`이 모델을 라우팅하지 못한 것——문제는 description에 있지 본문에 있지 않다.
- **서브에이전트의 fan-out**을 따로 표시한다. 이게 핵심이다. 서브에이전트는 자기만의 독립 컨텍스트에서 돌며, 메인 세션의 CLAUDE.md를 자동으로 상속하지 않는다. "분명히 규칙을 썼는데 서브태스크가 안 지킨다"의 다수는, 작업을 한 게 서브에이전트이고 그 규칙을 한 번도 읽은 적이 없기 때문이다. 타임라인에서 fan-out을 봐야 비로소, 규칙을 서브에이전트가 닿을 수 있는 곳까지 내려야 한다는 걸 깨닫는다.
- 도구 호출, 모델의 사고, 정체, 재시도를 같은 시간 축에 놓아, "이 단계에서 무엇을 호출하고 어디에 시간을 썼는지"가 한눈에 보인다.

요컨대, 내장된 `/context`·`/memory`는 "컨텍스트에 무엇이 있는가"에 답하고, 프로파일러는 "에이전트가 실제로 무엇을 했는가"에 답한다. 양쪽이 맞아떨어져야 비로소 확인했다고 할 수 있다.

### Codex 쪽: 모델에 보낸 것을 그대로 디스크에 떨군다

Codex는 더 철저한 길도 제공한다. 환경 변수 `CODEX_ROLLOUT_TRACE_ROOT`(`rollout-trace/src/thread.rs`)를 설정하면, 추론마다의 요청·응답·도구 호출 같은 원시 이벤트와 payload를 로컬 bundle로 디스크에 써내고, 나중에 오프라인 reducer가 "모델이 실제로 본 conversation items의 열"을 재구성한다. 이것이 가장 단단한 ground truth다. 읽었는지를 추측하는 게 아니라, 진짜로 모델에 보낸 것을 그대로 저장해 항목마다 대조한다. 세션 단위 rollout 영속화는 `core/src/session/mod.rs` 근처에 있다.

### "반드시 먹히게" 하려면, 길은 둘뿐

한 바퀴 돌아, 결론은 짧다. 컨텍스트 안의 글자는 엄격히 실행된다는 보장이 없다. 어떤 규칙을 정말 "반드시" 먹히게 하려면, 길은 둘뿐이다. system prompt 레벨로 끌어올리거나(CC의 `--append-system-prompt`, 또는 조직 레벨 managed 설정), 아예 "모델을 설득하는" 길을 버리고 hook과 권한 규칙으로 클라이언트 측에서 동작을 직접 막거나. 전자는 준수될 확률을 높이고, 후자는 모델에게 선택의 여지 자체를 주지 않는다.

## 요약

> **설정했다고 로드된 게 아니고, 로드됐다고 읽힌 게 아니며, 읽혔다고 따르는 게 아니다.**

지식 베이스를 연결하는 어느 방식이든 이 사슬의 다른 지점에서 막힌다. CLAUDE.md와 규칙은 "언제·어떤 신분으로 컨텍스트에 들어가는가", skill은 "description이 라우팅시켰는가", MCP는 "차지하는 컨텍스트만큼의 값을 하는가", 권한은 사슬 밖으로 나가 클라이언트 측에서 단단히 막는다.

디버깅할 때는, 먼저 `/context`·`/memory`·`InstructionsLoaded`로 그것이 윈도에 들어갔는지 확인하고, 다음으로 실제 한 번의 실행 트레이스로 에이전트가 무엇을 했는지——skill이 발화했는지, 서브에이전트가 규칙을 상속했는지——확인한다. 확실성을 원한다면, 컨텍스트 안의 글자가 엄격히 실행될 거라는 데 걸지 말고, system prompt로 끌어올리거나 hook과 권한에 맡긴다.

다음 장은 장기 태스크의 줄기로 돌아간다. harness가 여러 턴에 걸친 세션을 어떻게 버티는가——compaction·memory·goal이 어떻게 맞물리는가.
