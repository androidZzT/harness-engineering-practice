# 복잡한 작업의 Spec은 어떻게 쓰는가

이전 글에서 harness와 비즈니스 엔지니어링의 경계를 명확히 했다：harness는 플랫폼 층이고, 비즈니스 엔지니어링은 그 위에 구축되며 harness를 수정하지 않는다. 글 말미에 한 가지 질문을 남겼다：비즈니스 측의 spec에는 정확히 무엇을 써야 하는가.

이 글에서 정면으로 답한다. 단순한 작업은 한 문장 던져 모델에 맡기면 된다. 하지만 작업이 여러 역할의 협력、여러 단계 진행、각 단계의 추적 가능성이 필요할 정도로 복잡해지면, spec은 더 이상 "하나의 프롬프트"가 아니라 구조를 갖춘 엔지니어링 자산 세트다. 이것을 네 가지 질문으로 나누어 설명한다：멀티 Agent 구현 방법、편성자 진입점에 무엇을 쓸지、rules/docs/skills 역할 분담、skill 계층화 방법.

## 1. 멀티 Agent：하나의 편성자 + 전문 실행자 팀

복잡한 작업의 첫 번째 결정은, Agent 한 명에게 처음부터 끝까지 혼자 하게 하지 않는 것이다.

컨텍스트가 폭발하고, 책임이 뒤섞이며, Agent 하나가 요구사항 분석도 하고 코드도 쓰고 리뷰도 하다 보면 나중에는 지금 어떤 역할인지, 어떤 규칙을 따라야 하는지조차 구분하기 어려워진다. 내 방법은 편성자 하나가 전문 실행자 팀을 이끄는 것이다.

편성자（진입점 Agent）는 편성과 마무리만 한다：지금 어떤 단계인지、게이트를 통과했는지、누구에게 파견해야 하는지、계속할지 여부를 판단한다. 직접 비즈니스 코드를 작성하지 않는다. 구체적인 일은 전문 서브 Agent에 파견하며, 각 서브 Agent는 완전히 새로운 컨텍스트에서 시작하여 이번에 필요한 지식만 가지고 간다.

실행자는 책임에 따라 역할을 나눈다. 내 시스템은 대략 다음과 같다：

- 요구사항 분석가：요구사항 문서와 범위를 구조화된 입력으로 분해
- 아키텍트：기술 설계、크로스 플랫폼 통합 계약 정의、ADR 작성, 구현 코드는 쓰지 않음
- 각 플랫폼 구현자：플랫폼별로 분리되어 각자 자신의 플랫폼만 담당
- 코드 리뷰어：보안、성능、규범、참고 구현 정합성 등 여러 차원에서 검증
- 테스트 엔지니어：테스트 기준 보완、먼저 실패하는 인수 테스트 작성
- 통합 엔지니어：엔드투엔드 빌드、설치、실행、로그、크로스 플랫폼 일관성 테스트
- 효율화 엔지니어：반복적으로 나타나는 패턴을 재사용 가능한 자산으로 정착

역할 구분에는 간과하기 쉬운 효과가 있다：**역할을 잘못 선택하면 분업 문제에 그치지 않고, 그 역할에 바인딩된 규칙 제약을 우회하게 된다.** 예를 들어 각 플랫폼 구현자는 해당 플랫폼의 하드 제약 목록을 자동으로 로드하지만, 아키텍트는 그렇지 않다. 구현자에게 맡겨야 할 일을 아키텍트에게 잘못 파견하면, 그 구현 층의 검사 전체가 무효화된다. 나도 이 실수를 한 번 했다：플랫폼 UI 구현을 아키텍트에게 잘못 파견했다가 몇 가지 관문을 우회하게 되었고, 시각적 정합성 문제가 다시 나타났다.

그래서 파견은 느낌으로 할 수 없다. 내 규칙은 먼저 단계에 따라 역할을 선택하고, "변경 파일 경로 → 역할"의 매핑 테이블로 쓰기 범위를 검증하는 것이다. 두 가지가 충돌하면 멈추고 명확히 하며, 절대 특정 Agent의 쓰기 범위를 임의로 확장하지 않는다. 또 하나의 규칙：크로스 플랫폼 변경은 한 Agent가 모두 처리하는 것을 금지하고, 먼저 아키텍트가 통합 계약을 산출한 후, 각 플랫폼 구현자가 격리된 쓰기 범위에서 병렬로 진행해야 한다.

병렬도 절제가 있어야 한다. 같은 주선에 서브 Agent를 최대 5개까지만 연결하며, 일반적으로 4개 병렬이고 5번째는 예비로만 남겨둔다. 각 서브 Agent를 파견할 때 명확히 선언한다：어떤 산출물을 내야 하는지、어떤 형식인지、어디에 쓸지、인수 조건이 무엇인지. 완료 후 먼저 산출물이 존재하는지、적합한지 검증한 다음 닫아 슬롯을 해제한다. 이 할당량과 산출물 검증 없이는 멀티 Agent가 금방 통제 불능의 동시 프로세스 무리가 된다.


## 2. 편성자 진입점（CLAUDE.md / AGENTS.md）에 무엇을 쓸까

편성자의 동작은 대부분 진입점 파일, 즉 `CLAUDE.md` 또는 `AGENTS.md`에 의해 결정된다. 이 파일을 잘 쓰느냐 못 쓰느냐가 전체 협업이 질서 있는지 혼란스러운지를 직접 결정한다.

나의 첫 번째 원칙은：**진입점에는 시작 인덱스와 하드 경계만 넣고, 구체적인 단계는 넣지 않는다.**

많은 사람들이 모든 규칙、모든 프로세스를 `CLAUDE.md`에 한꺼번에 욱여넣어 결국 수천 줄이 되고, 모델이 매번 시작할 때 전부 읽어야 해서 느리고 핵심도 파악하기 어려워진다. 올바른 방법은 진입점을 가볍게 유지하는 것이다：진입점은 모델에게 "작업이 들어오면 먼저 유형을 판단하고, 그다음 어떤 파일을 읽으라"는 것만 알려준다. 구체적인 단계는 skill에, 하드 규칙은 rules에, 역할 계약은 agents에, 배경과 결정 기록은 docs에 넣는다. 진입점 자체는 하나의 지도일 뿐이다.

두 번째는 편성자의 계약을 명확히 고정하는 것이다. 내 진입점 파일에는 "진입점 Agent 계약"이라는 섹션이 있으며, 핵심은 몇 가지다：

- 편성자이자 마무리자이며, 실행자가 아니다
- 단계、게이트、인계、계속 여부、파견 대상만 판단한다
- 소규모 기계적 수정、인덱스 업데이트、검증 실행은 직접 할 수 있고, 나머지는 기본적으로 서브 Agent에 파견한다
- 프로덕션 코드를 직접 변경하지 않으며, 게이트、리뷰、검증을 우회하지 않는다
- 치명적이지 않은 문제를 만나면, 멈추고 묻는 것이 아니라 먼저 owner、route、증거、다음 단계를 기록한다
- 치명적인 오류가 있거나 현재 게이트가 명확히 막혔을 때만 멈출 수 있다

특히 마지막 두 가지가 중요하다. 복잡한 워크플로에서 가장 두려운 것은 Agent가 작은 문제만 만나도 멈춰 서서 결정을 기다리는 것이다. 10분 동안 8번 묻는 일이 생긴다. "언제 기록하고 계속할지、언제 멈출 수 있는지"를 계약에 쓰면, 비로소 한 번에 전체 링크를 끝까지 달릴 수 있다. 마찬가지로 서브 Agent 파견은 편성자의 내부 동작이며, 매번 돌아와 "다음 것을 파견해도 되는가"를 물어서는 안 된다—범위 확대、파괴적 작업、리스크 수용、대외 발행 같은 것만 당신에게 돌아와 결정을 받아야 한다.

특별히 주의해야 할 함정이 있다：**생성된 진입점 파일을 직접 편집하지 말라.** 내 진입점의 진정한 권위 소스는 템플릿 파일이고, `CLAUDE.md`와 `AGENTS.md`는 도구를 사용해 템플릿에서 투영한 것이다. 투영된 파일을 직접 수정하면, 다음에 동기화할 때 덮어씌워진다. 이것은 멀티 Agent 협업에서 쉽게 빠지는 함정이다—규칙을 변경했다고 생각하지만, 실제로는 일회용 산출물을 변경한 것이다.

## 3. rules / docs / skills를 어떻게 구성하는가

spec은 프로세스만이 아니다. "지식、제약、단계를 각각 어디에 놓고 어떻게 서로 참조할지"도 포함한다. 나는 세 가지 디렉토리 유형으로 세 가지 서로 다른 질문에 답한다：

- skills：어떻게 하는가（구체적인 단계와 프로세스）
- rules：무엇을 반드시 지켜야 하는가（하드 제약、체크리스트）
- docs：왜 지금 이런 형태인가（아키텍처、배경、장기 결정 기록）

이 분류법의 핵심 장점은 같은 지식이 단 하나의 권위 있는 위치만을 가진다는 것이다. 프로세스가 바뀌면 skill을 고치고, 제약이 바뀌면 rule을 고치고, 특정 설계가 왜 그렇게 정해졌는지 추적하려면 docs를 보면 된다. 이곳저곳에 중복되고 서로 모순되는 설명이 있을 일이 없다.

### skill 파일 구조는 어떻게 생겼는가

각 skill은 하나의 디렉토리다. 표준 구조는 간단하다：

```
어떤 skill/
  SKILL.md       진입점：라우팅 + 책임 + 경계 + 출력 계약
  references/    필요에 따라 로드하는 긴 내용：방법론、템플릿、체크 섹션
  scripts/       확정적 스크립트（script-backed skill에만 있음）
```

테스트 샘플은 skill 디렉토리에 넣지 않고, skill 이름에 일대일 대응하는 평행한 evals 디렉토리에 넣는다（다음 글에서 설명한다）.

`SKILL.md` 자체도 고정된 골격이 있으며, 각 섹션이 모두 짧다：

- frontmatter：name、라우팅에 사용되는 description（"적용 / 미적용 / 전형적 트리거 표현" 포함 필수）、계층、리스크 등급、수동 검토 필요 여부
- 책임 경계：이 skill이 무엇을 관리하는가
- 적용과 미적용：언제 호출하고 언제 호출하지 않는가
- 작동 방식：최소한의 프로세스, 더불어 "언제 어떤 reference를 읽어야 하는가"
- 필요 시 로드하는 references：각 시나리오에 대응하는 reference 파일 목록
- 출력 및 검증：무엇을 산출하고 어떻게 통과 여부를 판단하는가

핵심은 하나다：**SKILL.md는 가볍게 유지해야 한다.** 이것은 모델이 "나를 써야 하는가、어떻게 쓰는가"를 빠르게 판단하는 라우팅 카드이며, 지식 베이스가 아니다. 플랫폼 세부 사항、안티패턴、긴 템플릿을 전부 여기에 쌓으면, 매번 호출할 때마다 논문을 읽게 되어 호출 판단이 오히려 묻혀버린다.

### skill이 rule、docs、지식 베이스를 어떻게 참조하는가

skill 본문이 가볍다면, 실제 긴 지식은 어디에 있고 어떻게 사용되는가? 세 가지 다른 참조 방식으로, 각기 다른 유형을 관리한다.

**references는 skill 자신의 긴 내용이며, 필요에 따라 이름을 지정해 로드한다.** 방법론과 템플릿을 `SKILL.md`에 쓰는 것이 아니라, references 아래의 독립 파일로 분리하고, "작동 방식"에서 "이 단계에서는 어떤 reference를 읽으라"고 명확히 쓴다. 모델은 실제로 그 단계에 도달했을 때만 컨텍스트로 읽어들이며, 평소에는 공간을 차지하지 않는다.

**rule은 skill 본문에 복사하지 않고, 경로와 역할을 통해 자동으로 연결된다.** 하나는 디렉토리 레벨 규칙이다：각 규칙은 어떤 경로를 관리하는지 선언하며, Agent가 그 경로에 진입하면 규칙이 자동으로 컨텍스트에 로드된다；또 하나는 역할 바인딩으로, 특정 역할이 파견될 때 지켜야 할 체크리스트가 자동으로 함께 로드된다. 가장 하드한 몇 가지 제약은 경로에 연결되지 않고 시작 시 항상 상주한다. 이렇게 하면 규칙의 권위 소스는 하나뿐이고, skill과 역할은 모두 그것을 "참조"하는 것이지 각자 복사본을 가지는 것이 아니다.

**docs는 소비되는 지식 베이스이며, 참조 관계는 반드시 명시적이어야 한다.** docs에는 장기 지식과 결정 기록이 있으며, skill은 배경이 필요할 때 읽는다. 내가 특별히 중요시하는 규율이 하나 있다：**docs의 모든 장기 지식에는 명확한 소비자（특정 skill、rule 또는 역할）의 참조가 있어야 한다.** 소비자가 없는 지식은 고아 지식이다—써놓아도 아무도 읽지 않고、수정해도 아무도 모르고、천천히 실제와 괴리된다. 새로운 docs 지식을 추가할 때 누가 그것을 사용하는지 함께 기입하면, 이 지식은 비로소 진정으로 시스템에 진입한 것이지, 아무도 보지 않는 폴더에 쌓인 것이 아니다.

세 가지가 합쳐져 하나의 참조 네트워크를 이룬다：skill 본문은 가볍고, 자신의 references를 이름 지정해 읽으며, 경로와 역할 바인딩된 rule이 수동으로 연결되고, docs에서 배경을 능동적으로 가져오며, 각 지식은 단 하나의 권위 있는 위치를 가진다.


### scripts는 어떻게 구성하는가

scripts 디렉토리에는 확정적 도구들이 들어간다：검증기、명령 래퍼、프로세스 보조 스크립트. 그 존재 의미는 **Agent의 자유 즉흥 공간을 줄이는 것**이다. 유일하게 올바른 방법이 있는 것은 매번 모델이 새로 만들도록 두지 말고, 스크립트로 고정시킨다.

스크립트에 몇 가지 하드 요구사항이 있다：표준 라이브러리와 POSIX shell을 우선 사용하고 외부 의존성을 줄인다；상태 파일을 쓸 때는 원자적 쓰기를 해야 하며 동시성에는 잠금을 건다；명령 래퍼는 설정에서 선언한 진입점만 호출하고, 완전한 로그를 디스크에 남기며 메인 세션에는 요약만 전달한다. 또 쉽게 게으름 피우는 부분：새 스크립트에는 반드시 테스트를 작성하고, 프로세스 스크립트를 수정하면 회귀 테스트를 돌려야 하며, 문법 검사만 통과하는 것으로는 충분하지 않다. 스크립트는 확정성을 보장하기 위한 것이며, 스크립트 자체가 신뢰할 수 없으면 의미가 없다.

## 4. skill은 어떻게 계층화하는가, 왜 계층화하는가

마지막 조직 층은 skill 내부의 계층화 방식이다.

내 skill은 세 층으로 나누며, 책임이 엄격히 겹치지 않는다：

- 편성 층（orchestrator）：보통 하나만 있으며, 상태 기계를 유지하고 제어권을 파견하며, 구체적인 일은 하지 않는다
- 단계 층（phase）：산출 링크의 각 구간에 대응한다. 예를 들어 요구사항、설계、개발、리뷰、테스트、릴리스, 각 구간이 자신의 입출력과 게이트를 관리한다
- 원자 층（atom）：가장 아래의 단일 확정 능력, 각자 하나의 일만 하고, 다른 skill을 편성하지 않으며, 명령을 새로 발명하지도 않는다


단계 층에는 gate라는 핵심 설계가 있다. 각 단계 종료는 단순한 "완료"가 아니라 네 가지 상태의 결론을 내린다：pass（통과）、blocked（차단, 담당자와 롤백 경로 첨부）、not_required（이 단계는 해당 모듈에 적용 불필요）、risk_accepted（문제가 있지만 명시적으로 수용됨）. 예를 들어 어떤 모듈이 인터페이스를 전혀 렌더링하지 않는다면 UI 복원 단계에서 바로 not_required를 써서 통과시킨다；하지만 필요한 설계 참고가 없다면 억지로 감으로 조정하지 않고 blocked를 표시해 업스트림으로 반환하여 보완한다. **증거가 없을 때는 완료한 척하기보다 차단되는 것이 낫다.**

머리 속에서만 세 층을 나누면 소용없다. 기계가 읽고 검증할 수 있는 것으로 만들어야 한다. 나는 전체 그래프를 하나의 목록 파일로 만들어, 모든 skill의 단일 사실 소스로 삼는다. 각 노드는 고정 필드를 선언한다：어느 층에 속하는지、어떻게 실행하는지（스크립트가 연결되어 있는지 모델로 진행하는지）、라우팅에 사용하는 description（"적용 / 미적용 / 전형적 트리거 표현" 포함 필수）、입출력、사용 가능한 도구、리스크 등급、수동 검토 필요 여부.

노드 사이는 세 종류의 edge로 연결된다：

- handoff：단계 사이의 이동, 편성자가 구동
- dynamic_load：현재 작업 유형에 따라 서브 Agent의 새로운 컨텍스트에서 해당 능력을 동적으로 로드, 사용하는 것만 로드하고 전부 넣지 않는다
- semantic：증거 의존. 예를 들어 "후보 발견" 단계는 후보 지도만 생성하고, 실제 정확한 증거는 다운스트림 증거 skill이 수렴해야 하며, 후보를 보고 결론으로 삼으면 안 된다


그렇다면, **왜 반드시 계층화해야 하는가?** 이 일들의 변화 빈도와 실패 패턴이 완전히 다르기 때문이다. 편성 로직은 거의 변하지 않지만, 변하면 전역적이다；단계 계약은 중간 빈도로 변하며, 특정 구간의 입출력이 변한다；원자 능력은 가장 자주 변하지만, 매번 한 점만 변한다. 섞어놓으면 한 층만 변경하면서 다른 층이 무너지지 않을까 걱정할 수가 없다. 계층화 후에는 각 능력을 독립적으로 라우팅하고、독립적으로 테스트하고、독립적으로 수정할 수 있으며, 다른 부분을 조용히 끌어당기지 않는다.

## 한 문장 기억하기

> **복잡한 작업의 spec, 핵심은 세 가지 자산이다：워크플로 편성 방법、skill 조직 방법、지식 베이스 연결 방법. 이 세 가지를 각각 명확히 하는 것이 더 긴 프롬프트를 쓰는 것보다 훨씬 효과적이다.**

돌아보면 이 글은 정확히 이 세 가지 자산을 다루고 있다.

**워크플로 편성**은 앞의 두 섹션이다：멀티 Agent는 일을 누구에게 나누고 각자 어떤 규칙을 지키는지를 결정하고；편성자 진입점은 어디서 시작하는지、누가 결정권을 가지는지、어떻게 문제를 기록하면서 중단 없이 끝까지 달리는지를 결정한다.

**skill 조직**은 3、4섹션을 관통한다：하나의 skill 파일을 어떻게 배치하는지（가벼운 진입점 + 필요에 따라 로드하는 긴 내용 + 확정적 스크립트）, 전체 skill을 편성、단계、원자 세 층으로 어떻게 나누어 능력이 늘어날수록 혼란스럽지 않게 하는지.

**지식 베이스 연결**은 세 번째 섹션의 참조 네트워크다：rule은 경로와 역할을 통해 자동으로 연결되고、docs의 모든 지식은 소비자가 있어야 하며、skill은 자신의 references만 이름 지정해 읽는다. 하나의 지식은 하나의 권위 있는 위치만 가지며, 한 곳을 변경하면 어디서나 효과를 발휘하고, 서로 모순되는 복사본이 생기지 않는다.

이 세 가지가 합쳐지면 "AI가 정확히 무엇을 하는지"가 추적 가능해진다：각 단계를 누가 해야 하는지、어떤 규칙을 지켜야 하는지、어떤 증거를 산출해야 하는지、차단되면 어디로 돌아가는지가 모두 spec에 있으며, 어느 대화의 임기응변 속에 숨어있지 않다.

이것은 첫 번째 글과 같은 주제다—절제. 능력이 함부로 자라지 않도록, 하나를 추가할 때마다 그것의 위치와 계약을 명확히 한다.

하지만 spec을 잘 쓰는 것은 "조직이 명확한지"만 해결할 뿐, "각 skill이 실제로 잘 작동하는지"는 아직 해결하지 못했다. 라우팅 description을 아무리 잘 써도, 모델이 정말 올바른 순간에 호출할까? 어떤 단계가 게이트 결론을 산출하겠다고 했는데, 실제로 매번 산출하고 있을까? 이것들은 테스트가 필요하다.

다음 글에서는 skill이 실제로 잘 작동하는지 테스트하는 방법을 설명한다. 주로 세 가지다.

첫째, 대조를 어떻게 하는가. 같은 문제를 모델에게 이 skill을 붙여 한 번, 붙이지 않고 한 번 돌려서, 두 번의 출력 차이가 어디에 있는지 비교한다. 이렇게 해야만 좋은 부분이 이 skill 덕분인지, 아니면 일반 규칙이 원래 할 수 있는 것인지 알 수 있다. 공을 잘못 돌리는 일이 없다.

둘째, 결과를 어떻게 저장하는가. 모델의 매번 실제 응답을 파일로 저장하고 코드 베이스에 커밋하여, 누구나 언제든지 꺼내 재확인할 수 있고, 실행 후 잊어버리거나 다음에 또 다른 결과가 나오는 일이 없도록 한다.

셋째, 왜 다른 대형 모델에게 채점하게 하지 않는가. AI를 심판으로 삼는 것은 편리해 보이지만, 심판 자체도 불안정하여 오늘은 8점 내일은 6점이다. 나는 오히려 옳고 그름이 한눈에 보이는 고정된 검사 항목 세트를 사용해 판단하겠다.
