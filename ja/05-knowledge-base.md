# Spec と知識ベース：エージェントが本当に読み、本当に従っているかを確かめる

プロジェクトに CLAUDE.md を書き、ルールをいくつか切り出し、skill をいくつか作り、MCP サーバーを 2 つつないだ。それでもエージェントは相変わらず同じミスを犯し、決めたルールを見なかったことにする。

そこであなたは一つのことを疑い始める。そもそも読んでいるのか？

この問いは見た目より価値がある。「ファイルを 1 つ設定した」と「そのファイルの中身がこのステップでのモデルの判断に本当に影響した」の間には、いくつものゲートがあり、どれもがこっそり取りこぼしうる。私はそれを、一つにまとめられがちな 4 つのことに分けている。

> **紐付け ≠ ロード ≠ 読まれた ≠ 遵守。**

`.claude/` にファイルを置くのが「紐付け」。それがこのセッションでコンテキストウィンドウに差し込まれるのが「ロード」。モデルが現在のステップで実際にそれを判断に取り込むのが「読まれた」。その通りに動いて初めて「遵守」。4 つのどの 1 つが切れても結果は同じ「ルールが効かなかった」だが、どこで切れたかでデバッグの仕方はまったく変わる。

この章ではまず知識ベースをつなぐいくつかの方法を一通り見て、次にそれぞれが「いつ・どんな形で」コンテキストに入るかを説明し、最後に本当に入ったか・本当に制約したかをどう確かめるかを述べる。いつも通り Claude Code（以下 CC）と Codex を並べて見る。CC 側は公式ドキュメントに基づき控えめな言い回しで、Codex 側はソースの行番号まで辿れるものは出典を付けた。

## 1. 知識ベースがエージェントに届く経路

まず「知識ベース」をはっきりさせておく。ここでは、エージェントに守り続けてほしいもの——プロジェクトの取り決め、コーディング規約、ワークフロー、ドメイン知識、呼び出せる能力、外部データを指す。これらをエージェントにつなぐ仕組みは、CC と Codex でほぼ一対一に対応する。

| 仕組み | Claude Code | Codex |
|---|---|---|
| 主指示ファイル | CLAUDE.md：プロジェクト / ユーザー / 組織のスコープ、加えてサブディレクトリの CLAUDE.md | AGENTS.md：グローバル / プロジェクト / サブディレクトリの多段 |
| 分割ルール | `.claude/rules/`：複数ファイルに分割、ファイルパスでスコープ可 | config 内の instructions：設定に付いて回る指示 |
| 自動メモリ | Auto memory：モデルが自分でためるメモ、入口は `MEMORY.md` | —— |
| スキル | Skill：トリガー条件付きのロード可能な振る舞い単位 | skill：同じ概念、呼び方が少し違う |
| 外部ツール / データ | MCP | MCP |
| 特殊な注入口 | `@import`、`--append-system-prompt` | —— |

これらの経路は似て見えるが、効いてくる違いはすべて次の節にある。コンテキストに入る「タイミング」と「形」が異なること、それが「設定したのに効かない」の根源だ。

## 2. 各経路はどうコンテキストに入るか

違いは 3 つに潜んでいる。いつコンテキストに入るか、どんな立場で入るか、どこでこっそり漏れるか。まず骨格を 1 つの表で示し、ソース出典は表の下に置く。

| 経路 | いつコンテキストに入るか | どんな立場 / 形で | 一番つまずく点 |
|---|---|---|---|
| CLAUDE.md / AGENTS.md | 起動時に「起動ディレクトリから上」へ辿る連鎖がロードされる。サブディレクトリのものはエージェントが実際にそのディレクトリのファイルを読みに行って初めて入る | user メッセージとして注入され、system prompt ではない——context であって、強制設定ではない | 今回触らなかったサブディレクトリのルールはずっと不在。AGENTS.md はデフォルト 32 KiB 上限、超えると切り捨て（軽視ではなく、入っていない） |
| `.claude/rules/` | `paths:` 付きは glob パスでトリガー。`paths` なしのものだけ起動時に全量ロード | CLAUDE.md と同じく user 側に乗る | `paths` を書いたのに対応ディレクトリを触っていない → ルールが発火しない。これはバグではなく設計 |
| skill | 起動時はメタデータ（名前 + `description`）のみ。本文はトリガーされて初めてロード | progressive disclosure：未使用ならほぼトークンを食わないが、一度ロードされると以降毎ターン常駐 | `description` がマッチしない → 本文は一文字も入らない。「発見 / ロード / トリガー」は別の 3 つ |
| MCP | ツール定義（schema）が起動時にコンテキストへ入る | トークンを食うツール一覧 | 多くマウントし、各ツールも多い → 先に大きなコンテキストの「家賃」を払う |
| 権限 / hook | ツールが実際に実行される直前で割り込む、**モデルの意思を経由しない** | クライアント側の硬い制約、上記「コンテキストに入る」連鎖の外 | 「モデルがどう思おうと止めたい」なら CLAUDE.md に書かず、deny ルールか PreToolUse hook を使う |

覚えておく価値のある細部と出典をいくつか：

- **CLAUDE.md**：公式の位置づけは context であって enforced configuration ではない。そこに書く「必ず / 絶対に」は本質的にスイッチではなく要請。`@import` は起動時に展開、最大 4 ホップ。ブロックレベルの HTML コメントは注入前に剥がされるので、トークンを食わずに人間向けのメモを残せる。
- **AGENTS.md**：多段の発見は `core/src/agents_md.rs`、32 KiB 上限は `AGENTS_MD_MAX_BYTES`（`core/src/config/mod.rs:186`）。`# AGENTS.md instructions ...` / `</INSTRUCTIONS>` タグで包まれた user 指示（`core/src/context/user_instructions.rs`）として、config instructions とマージされる。
- **skill**：一覧内のメタデータには上限があり、`description` + `when_to_use` 合算で 1536 文字を超えると切り捨て。Codex 側はメタデータを予算に合わせてレンダリングし developer メッセージに差し込む（`core/src/session/mod.rs` の `build_available_skills`）。
- **MCP**：ツールは接続マネージャから列挙し、アクセス可能かつ有効なものに絞って指示に差し込む（`core/src/connectors.rs`）。
- **権限**：CC は `allow` / `ask` / `deny` の 3 配列で、判定は deny > ask > allow、さらに permission mode（default / acceptEdits / plan / bypassPermissions）を重ねる。Codex は型システムに落とし込む——`SandboxPolicy` は 4 値（`protocol/src/protocol.rs:878`）、`AskForApproval` は 5 値（`:784`）、細粒度の `GranularApprovalConfig`（`:817-854`）が skill / rules / MCP それぞれに都度確認の要否を分けて管理できる。

この節を一言で締める：**CLAUDE.md / ルール / skill の中の言葉はモデルに見せる提案、権限と hook はあなたの代わりに動作を止めるゲート。「必ず」が欲しいなら後者を使う。**

## 3. エージェントが本当に読み、本当に制約されたかをどう確かめるか

これがこの章で最も解くべき問いだ。先の「紐付け ≠ ロード ≠ 読まれた ≠ 遵守」の連鎖をばらすと、検証手段も 2 層に分かれる。1 つはものがコンテキストウィンドウに入ったか（静的）、もう 1 つはエージェントが実際に何をしたか（振る舞い）。

### まず：ものは本当にコンテキストに入ったか

CC にはいくつか既製の窓口がある。

- **`/context`**：現在のコンテキストウィンドウのトークン内訳を見る——system prompt、ツール、MCP、メモリファイル、メッセージがそれぞれどれだけ占めるか。最も直接的な判断は、ロードされたつもりのものがここに取り分を持たないなら、入っていない。
- **`/memory`**：このセッションで実際にロードされた CLAUDE.md、CLAUDE.local.md、rules ファイルを列挙する。この一覧にないファイルはモデルには見えない。「CLAUDE.md が効かない」のデバッグは、まずこれを走らせてファイルが一覧にあるか確かめるところから。
- **`InstructionsLoaded` hook**：正確なログが欲しければ、この hook でどの指示ファイルが・いつ・なぜロードされたかを記録できる。path-scoped ルールやサブディレクトリの遅延ロードされるファイルのデバッグに特に向く。

前述の仕組みから直接導ける確認動作もいくつか：サブディレクトリの CLAUDE.md、`MEMORY.md` の 200 行を超える内容、topic ファイルは起動時にはコンテキストに入らない。効いているか確かめるには、モデルが実際に対応ディレクトリのファイルを read しに行ったかを見る。`/compact` の後、プロジェクトルートの CLAUDE.md はディスクから読み直されて再注入されるが、サブディレクトリのものはされない。圧縮後にルールが「緩む」のはたいていこれが原因だ。

### 次に：エージェントは実際に何をしたか

静的チェックは「ものがウィンドウにあるか」は教えてくれるが、「その skill が今回本当にトリガーされたか」「派遣したサブエージェントがあなたのルールを継承したか」には答えられない。これらは振る舞い層の問題で、実際の 1 回の実行トレースを見る必要がある。

この層には、オープンソースのプロファイラ、例えば [cctrace](https://github.com/androidZzT/cctrace)（Go 製、MIT、ローカル実行、非通信）が使える。あなたのエージェントを 1 枚かぶせ（`cctrace claude -- claude` か `cctrace codex -- codex`）、その実行のイベントをローカルのウォーターフォール・タイムラインに並べる。この章の問いに対して、ちょうど噛み合う機能がいくつかある。

- セッション起動時に「このマシンでどの skill が発見されたか、そしてその description」を集め、タイムライン上に「今回どの skill が実際にトリガーされたか」を印す。両者を突き合わせれば判断できる。ある skill が一覧にあるのに最後まで一度も fire しなければ、その `description` がモデルをルーティングできなかった——問題は description にあり、本文にはない。
- **サブエージェントの fan-out** を別に印す。これが肝心だ。サブエージェントは自分の独立したコンテキストで動き、メインセッションの CLAUDE.md を自動では継承しない。「ルールを書いたのにサブタスクが守らない」の多くは、作業をしたのがサブエージェントで、そのルールを一度も読んでいないからだ。タイムラインで fan-out を見て初めて、ルールをサブエージェントが手に取れる場所まで降ろすべきだと気づく。
- ツール呼び出し、モデルの思考、停滞、リトライを同じ時間軸に並べるので、「このステップで何を呼び、どこに時間を使ったか」が一目でわかる。

要するに、組み込みの `/context`・`/memory` は「コンテキストに何があるか」に答え、プロファイラは「エージェントが実際に何をしたか」に答える。両側が揃って初めて確認したと言える。

### Codex 側：モデルに送られたものをそのままディスクに落とす

Codex はもっと徹底した道も用意している。環境変数 `CODEX_ROLLOUT_TRACE_ROOT`（`rollout-trace/src/thread.rs`）を設定すると、推論ごとのリクエスト・レスポンス・ツール呼び出しといった生イベントと payload をローカルの bundle としてディスクに書き出し、後でオフラインの reducer が「モデルが実際に見た conversation items の列」を再構成する。これは最も硬い ground truth だ。読んだかどうかを推測するのではなく、本当にモデルへ送られたものをそのまま保存し、項目ごとに突き合わせる。セッション単位の rollout 永続化は `core/src/session/mod.rs` あたりにある。

### 「必ず効かせる」には、道は 2 つしかない

一周して、結論は短い。コンテキスト内の文字は厳密に実行される保証がない。あるルールを本当に「必ず」効かせたいなら、道は 2 つだけ。system prompt のレベルに引き上げる（CC の `--append-system-prompt`、または組織レベルの managed 設定）か、いっそ「モデルを説得する」道をやめて、hook と権限ルールでクライアント側で動作を直接止める。前者は遵守される確率を上げ、後者はモデルに選ぶ余地そのものを与えない。

## まとめ

> **設定した、はロードした、ではない。ロードした、は読まれた、ではない。読まれた、は従う、ではない。**

知識ベースをつなぐどの方法も、この連鎖の異なる地点で詰まる。CLAUDE.md とルールは「いつ・どんな立場でコンテキストに入るか」、skill は「description がルーティングさせたか」、MCP は「占めるコンテキストに見合うか」、権限は連鎖の外に出てクライアント側で硬く止める。

デバッグでは、まず `/context`・`/memory`・`InstructionsLoaded` でものがウィンドウに入ったかを確かめ、次に実際の 1 回の実行トレースでエージェントが何をしたか——skill が発火したか、サブエージェントがルールを継承したか——を確かめる。確実性が欲しいなら、コンテキスト内の文字が厳密に実行されることに賭けず、system prompt に引き上げるか、hook と権限に委ねる。

次の章は長時間タスクの線に戻る。harness が多ターンにまたがるセッションをどう支えるか——compaction・memory・goal がどう連携するか。
