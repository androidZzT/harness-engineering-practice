# 複雑なタスクの spec の書き方

前稿では harness と業務工学の境界を明確にした：harness はプラットフォーム層であり、業務工学はその上に構築するものであって変更すべきではない。最後に問いを残した：業務側の spec には具体的に何を書くべきか。

本稿ではその問いに正面から答える。単純なタスクならモデルに一言投げれば済む。しかしタスクが複数の役割の協働を要し、複数フェーズにまたがり、各ステップの追跡可能性も保証しなければならないほど複雑になると、spec はもはや「ひとつのプロンプト」ではなく、構造を持つ工学資産の一式になる。これを四つの問いに分けて論じる：マルチ Agent の落とし込み・オーケストレーターエントリポイントの書き方・rules / docs / skills の分担・skill の階層化。

## 一、マルチ Agent：一つのオーケストレーター＋専従実行者チーム

複雑なタスクにおける最初の決断は、一つの Agent に最初から最後まで任せないことだ。

コンテキストは溢れ、責務は曖昧になる。一つの Agent が要件分析もコード記述もレビューも行うと、最終的には自分が今どの役割でいて何のルールを守るべきかすら見失う。私のやり方は、一つのオーケストレーターが専従実行者チームを率いる形だ。

オーケストレーター（エントリ Agent）はオーケストレーションとクローズだけを行う：現在のフェーズを判断し、gate を通過しているか確認し、誰に派遣するか決め、継続するかどうか決める。業務コードを自分で書くことはしない。具体的な作業は専従サブ Agent に派遣し、各サブ Agent は新しい独立したコンテキストで起動し、自分がそのタスクで必要とする知識だけを持つ。

実行者は役割に応じて分割し、私のシステムでは概ね次のような役割がある：

- 要件アナリスト：要件文書とスコープを構造化された入力に分解する
- アーキテクト：技術設計・クロスプラットフォーム統一契約の策定・ADR の記述を行うが実装コードは書かない
- 各プラットフォーム実装者：プラットフォームごとに分け、各自の範囲だけを書く
- コードレビュアー：セキュリティ・パフォーマンス・規約・参照実装への整合という複数の観点から検証する
- テストエンジニア：テスト基準を補完し、先に失敗する受け入れテストを書く
- 結合テストエンジニア：エンドツーエンドのビルド・インストール・実行・ログ・クロスプラットフォーム一貫性を確認する
- 効率化エンジニア：繰り返し現れるパターンを再利用可能な資産として蓄積する

役割の分割には見落とされがちな効果がある：**役割の選択を誤ると分担が狂うだけでなく、その役割に紐付くルール制約を迂回してしまう。** 例えば各プラットフォーム実装者は対応するプラットフォームのハード制約リストを自動的にロードするが、アーキテクトはしない。実装者に渡すべき作業をアーキテクトに誤って派遣すると、その実装層のチェックがまるごと無効になる。私自身この失敗をやらかしている：あるとき UI 実装をアーキテクトに誤派遣し、通過すべきいくつかの関門を飛ばしたことで、ビジュアル整合の問題が再浮上した。

だから派遣は感覚ではいけない。私のルールは、まずフェーズで役割を選び、次に「変更ファイルパス → 役割」のマッピング表で書き込み範囲を検証し、両者が衝突したら止めて明確にする。ある Agent の書き込み範囲を無断で拡大することは絶対しない。もう一つのルール：クロスプラットフォームの変更を一つの Agent に全部任せることは禁止。必ずアーキテクトが統一契約を出してから、各プラットフォーム実装者がアイソレートされた書き込み範囲で並行作業する。

並行にも節度が必要だ。同一のメインラインに最大 5 個のサブ Agent を吊り下げ、通常並行は 4 個、5 個目は予備として残す。各サブ Agent を派遣する際には明示する：何の成果物を、どの形式で、どこに書き、受け入れ条件は何か。完了後は成果物が存在し合格しているかを先に検証してからクローズして枠を解放する。このクォータと成果物検証がなければ、マルチ Agent はすぐに制御不能な並行プロセス群になる。


## 二、オーケストレーターエントリポイント（CLAUDE.md / AGENTS.md）に書くこと

オーケストレーターの挙動はほぼそのエントリファイル、すなわち `CLAUDE.md` または `AGENTS.md` で決まる。このファイルをうまく書けるかどうかが、協働全体が秩序あるものになるか混乱に陥るかを直接決める。

私の第一の原則は：**エントリには起動インデックスとハード境界だけを置き、具体的なステップを置かない。**

多くの人がすべてのルール・すべてのプロセスを `CLAUDE.md` に一気に詰め込み、最終的に数千行になる。モデルが起動のたびに読み込まなければならず、遅いうえに要点が掴めない。正しいやり方はエントリを薄くすることだ：モデルに伝えるのは「タスクが来たらまず種類を判断し、次にどのファイルを読むか」だけ。具体的なステップは skill に、ハードルールは rules に、役割契約は agents に、背景と意思決定記録は docs に置く。エントリ自体は地図にすぎない。

第二は、オーケストレーターの契約をきちんと書き込むことだ。私のエントリファイルには「エントリ Agent 契約」というセクションがあり、核心はほんの数文だ：

- オーケストレーターとクローズ担当であって、実行者ではない
- フェーズ・gate・引き継ぎ・継続判断・派遣先だけを決める
- 小規模な機械的修正・インデックス更新・検証実行は自分でやってよい、それ以外はデフォルトでサブ Agent に派遣する
- 本番コードは直接変更しない、gate・レビュー・検証を迂回しない
- 致命的でない問題に直面したときは、停止して確認を求めるのではなく、owner・route・証跡・次のステップを記録して継続する
- 致命的なエラー、または現在の gate が明確にブロックされている場合のみ停止を許可する

最後の二つは特に重要だ。複雑なワークフローで最も困るのは、Agent が小さな問題のたびに止まって判断を求めてくることで、10 分動いて 8 回確認してくる。「どんな状況で記録して継続し、どんな状況なら停止してよいか」を契約に書いておくことで、本当に一気に処理チェーンを走り切れるようになる。同様に、サブ Agent の派遣はオーケストレーターの内部動作であり、毎回「次を派遣してよいか」と聞いて戻ってくるべきではない——スコープ拡大・破壊的操作・リスク受け入れ・対外公開といった場合だけ判断を求めればよい。

もう一つ特に注意すべき落とし穴がある：**生成されたエントリファイルを直接編集しない。** 私のエントリの権威ある源泉はテンプレートファイルであり、`CLAUDE.md` と `AGENTS.md` はそのテンプレートからツールで投影されたものだ。投影されたファイルを直接変更すると、次の同期で上書きされる。マルチ Agent 協働ではこの落とし穴を踏みやすい——ルールを変えたつもりが、実は一時的な生成物を変えていたということになる。

## 三、rules / docs / skills の整理方法

spec はプロセスだけではなく、「知識・制約・ステップをそれぞれどこに置いてどう相互参照するか」も含む。三種類のディレクトリを使って三つの異なる問いに答える：

- skills：何をどうやるか（具体的なステップとプロセス）
- rules：何を必ず守るか（ハード制約・チェックリスト）
- docs：なぜ現在の状態になっているか（アーキテクチャ・背景・長期的な意思決定記録）

この分け方の核心的な利点は、同じ知識は一つの権威ある場所にしか存在しないことだ。プロセスが変われば skill を修正し、制約が変われば rule を修正し、ある設計がなぜそうなっているかを遡るなら docs を参照する。矛盾した説明が各地に散乱することがない。

### skill のファイル構造

各 skill は一つのディレクトリで、標準構造は単純だ：

```
ある skill/
  SKILL.md       エントリ：ルーティング＋責務＋境界＋出力契約
  references/    必要に応じてロードする長コンテンツ：方法論・テンプレート・チェックセクション
  scripts/       確定的スクリプト（script-backed skill のみ）
```

テストサンプルは skill ディレクトリには置かず、並列の evals ディレクトリに skill 名に対応させて置く（次稿で論じる）。

`SKILL.md` 自体も固定の骨格を持ち、各セクションは短い：

- frontmatter：name・ルーティングに使う description（「適用 / 非適用 / 典型的なトリガーフレーズ」を必ず含む）・レイヤー・リスクレベル・手動レビューが必要かどうか
- 責務境界：この skill が担う範囲
- 適用と非適用：いつ呼び出すか、いつ呼び出さないか
- 動作方法：最小限のプロセス、加えて「どの状況でどの reference を読むか」
- オンデマンドロード references：各シナリオに対応する reference ファイルを列挙したリスト
- 出力と検証：何を成果物とし、何をもって通過とするか

要点は一つ：**SKILL.md は薄くすること。** モデルが「自分を使うべきか・どう使うか」を素早く判断するためのルーティングカードであり、知識ベースではない。プラットフォームの詳細・アンチパターン・長いテンプレートを詰め込むと、呼び出すたびに論文を読ませることになり、呼び出し判断がかえって埋もれてしまう。

### skill が rule・docs・知識ベースをどう参照するか

skill 本文が薄いなら、本当の長い知識はどこにあってどう使われるのか。三種類の異なる参照方式がそれぞれ一種類を担う。

**references は skill 自身の長コンテンツで、必要に応じて名指しでロードする。** 方法論やテンプレートを `SKILL.md` に書き込まず、references 以下の独立したファイルに分割し、「動作方法」の中に「このステップではどの reference を読む」と明記する。モデルは実際にそのステップに到達したときだけ読み込み、普段はコンテキストを占有しない。

**rule は skill 本文にコピペせず、パスとロール（役割）への自動アタッチで参照する。** 一種はディレクトリレベルのルール：各ルールが管理するパスを宣言し、Agent がそのパスに入ると自動的にコンテキストにロードされる。もう一種はロールバインディング：ある役割が派遣されると、その役割が守るべきチェックリストが自動的についてくる。最もハードな制約は特定のパスに紐付けず、起動時から常駐する。こうすることでルールの権威ある源泉は一つだけとなり、skill と役割は「参照」するのみで、それぞれがコピーを持つことはない。

**docs は消費される知識ベースであり、参照関係は明示的でなければならない。** docs には長期的な知識と意思決定記録を置き、skill が背景を必要とするときに読みに行く。私が特に気にするルールがここにある：**docs 内の各長期知識には、明確な消費者（ある skill・rule・または役割）からの参照が必要だ。** 消費者のない知識はみなしご知識——書いても誰も読まず、変えても誰も知らず、やがて実態と乖離する。新しい docs の知識を追加するとき、誰が使うかを合わせて補記してはじめて、その知識はシステムに入ったと言える。誰も見ないフォルダに積まれるだけでなく。

三者合わせて一つの参照ネットワークになる：skill 本文は薄く、自身の references を名指しでロード、パスとロールバインディングで rule を受動的に受け取り、docs から背景を能動的に取得する。そして各知識には唯一の権威ある場所がある。


### scripts の整理

scripts ディレクトリには確定的ツールを置く：バリデーター・コマンドラッパー・プロセス補助スクリプト。存在意義は、**Agent が自由に発想するスペースを縮小すること**だ。唯一の正しいやり方がある物事は、モデルに毎回即興させず、スクリプトに固定する。

スクリプトにはいくつかのハード要件を設けている：標準ライブラリと POSIX shell を優先し、外部依存は少なく；状態ファイルの書き込みはアトミックに行い、並行処理はロックを使う；コマンドラッパーは設定で宣言されたエントリポイントだけを呼び出し、完全なログをディスクに記録しメインセッションには要約だけを返す。さぼりがちな点として：新しいスクリプトには必ずテストを付け、プロセススクリプトを変更したらリグレッションを実行し、構文チェックだけで終わらせない。スクリプトは確定性を担保するためにあり、スクリプト自体が信頼できなければ意味がない。

## 四、skill の階層化、なぜ階層化するか

最後の整理は、skill 内部の階層化だ。

私の skill は三層に分け、責務が厳密に重複しない：

- オーケストレーション層（orchestrator）：通常一つのみ、状態機械を保守し制御権を派遣する、具体的な作業はしない
- フェーズ層（phase）：成果物チェーンの各セグメントに対応、例えば要件・設計・開発・レビュー・テスト・リリース、各セグメントが自身の入出力と gate を管理する
- アトム層（atom）：最底層の単一確定能力、各アトムは一つのことだけを行い、他の skill をオーケストレートせず、コマンドを発明しない


フェーズ層には gate という重要な設計がある。各フェーズの終了は単純な「完了」ではなく、四択の結論を出す：pass（通過）・blocked（ブロック、担当者と差し戻しパスを添える）・not_required（このモジュールにはこのフェーズが不要）・risk_accepted（問題はあるが明示的に受け入れ済み）。例えば、あるモジュールがそもそも UI をレンダリングしないなら、UI 整合フェーズを `not_required` として通過させる；しかし必要なデザイン参照がなければ、感覚で進むのではなく `blocked` を返して上流に補完を求める。**証跡がないときは、完了したふりをするより止まる方がよい。**

頭の中だけで三層に分けても意味がない。機械が読めて検証できる形にする必要がある。全体の図を一つのリストファイルに落とし込み、これが全 skill の唯一の事実の源泉になる。各ノードは固定フィールドを宣言する：どのレイヤーに属するか・どう実行するか（スクリプトをバックエンドにするかモデルで進めるか）・ルーティング用の description（「適用 / 非適用 / 典型的なトリガーフレーズ」を必ず含む）・入出力・利用可能なツール・リスクレベル・手動レビューが必要かどうか。

ノード間は三種類の edge でつなぐ：

- handoff：フェーズ間の流転、オーケストレーターが駆動する
- dynamic_load：現在のタスク種別に応じて、サブ Agent の新しいコンテキストの中で対応する能力を動的にロードする、必要なものだけ使い、全部詰め込まない
- semantic：証跡依存、例えば「候補発見」ステップは候補マップだけを出力し、実際のピンポイント証跡は下流の証跡 skill で収束させる必要がある、候補を見たからといって結論にしてはならない


なぜ**必ず**階層化するのか。なぜならこれらの事物は変化の頻度と失敗のパターンがまったく異なるからだ。オーケストレーションロジックはほとんど変わらず、変わると全局的影響がある；フェーズ契約は中程度の頻度で変わり、変更はあるセグメントの入出力に限られる；アトム能力は最も頻繁に変わるが、変更は一点だけだ。混在させると、一層だけ変えても他の層が崩れないか心配しなければならない。階層化することで、各能力を独立してルーティングし・独立してテストし・独立して変更でき、他の部分をこっそり引きずることがない。

## 一文を覚えておく

> **複雑なタスクの spec の核心は三つの資産だ：ワークフローをどうオーケストレートするか・skill をどう整理するか・知識ベースをどうつなぐか。この三つを個別に明確にする方が、より長いプロンプトを書くよりずっと効く。**

本稿を振り返ると、ちょうどこの三つの資産に対応している。

**ワークフローオーケストレーション**は前二節：マルチ Agent は誰に何を守らせるかを決め；オーケストレーターエントリポイントはどこから入り誰が決定権を持ち、どう問題を記録しながら一気に走り切るかを決める——止まって確認を求めることなく。

**skill 整理**は第三・四節を貫く：skill のファイルの置き方（薄いエントリ＋オンデマンドロードの長コンテンツ＋確定的スクリプト）、skill 全体をオーケストレーション・フェーズ・アトムの三層に分けて能力が増えても混乱しないようにする。

**知識ベースのつなぎ方**は第三節の参照ネットワークだ：rule はパスとロールバインディングで自動アタッチ、docs の各知識は消費者が必要、skill は自身の references だけを名指しでロードする。各知識には唯一の権威ある場所があり、一箇所変えれば全体に反映され、矛盾したコピーが各地に散らばることがない。

三者合わせると、「AI が何をしているか」が追跡可能になる：各ステップを誰が担い・何を守り・何の証跡を出すべきか・ブロックされたらどこに戻るかが、spec に書かれており、ある会話のアドリブに隠れていない。

これは第一稿と同じテーマ——克制だ。能力を無制限に増やさず、追加するたびにその位置と契約を明確にする。

しかし spec をうまく書くことで「整理が明確か」の問題は解決できるが、「各 skill が本当に使えるか」はまだ解決できていない。ルーティング description がどれほど美しく書かれていても、モデルは必ず正しいタイミングで呼び出すのか。あるフェーズが gate の結論を出力すると宣言していても、本当に毎回出力しているか。これはテストで確かめるしかない。

次稿では skill が本当に使えるかをどうテストするかを論じる。主に三点だ。

第一に、対照をどう設ける。同じ問いで、モデルにこの skill を付けて一度実行し、付けずに再び実行して、二つの出力の差を比較する。こうして初めて、良かった部分がこの skill によるものか、汎用ルールでもともとできることかを見分けられ、功績を誤帰属しない。

第二に、結果をどう保存するか。モデルの実際の回答をすべてファイルとして保存しコードベースにコミットする。誰でもいつでも遡って確認でき、実行したら忘れて次回はまた全部新しい結果、ということにならない。

第三に、なぜ別の大モデルで採点しないのか。AI に審判をやらせると楽に聞こえるが、審判自体が安定しない——今日 8 点、明日 6 点だ。私はあらかじめ書き固めた、正誤が一目でわかる検査項目で判定する方を選ぶ。
